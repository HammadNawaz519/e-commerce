1. CONCEPTUAL OVERVIEW
================================================================================
Shopy uses LangChain's SQL Agent framework to implement a true text-to-SQL
pipeline. The AI assistant (Sage) performs REAL SQL generation:

  1. The user asks a question in plain English.
  2. LangChain's SQLDatabase wrapper inspects the live MySQL schema
     (table names, column types, sample rows) and builds full schema context.
  3. A LangChain SQL Agent — powered by the OpenRouter LLM via ChatOpenAI —
     reads the schema context and GENERATES a SQL SELECT statement.
  4. The generated SQL is validated (must start with SELECT) before execution.
  5. The validated SELECT query is executed against the read-only database
     using the readonly_app MySQL user (Principle of Least Privilege).
  6. The raw result rows are passed back to the LLM for synthesis into a
     human-readable English answer.
  7. The query, raw output, and final answer are returned in the same
     structured format so the existing UI displays them without any changes.

Dependency: LangChain (langchain, langchain-community, langchain-openai,
            sqlalchemy) — declared in requirements.txt.


================================================================================
2. LLM PROVIDER — OPENROUTER (MULTI-MODEL FAILOVER)
================================================================================
We use the OpenRouter API, which provides access to multiple LLM models
through a single API endpoint. Our system implements automatic model failover:

  Priority Order (defined in prompts.py, lines 403-409):
    1. Custom model from .env (OPENROUTER_MODEL)
    2. openai/gpt-oss-120b:free
    3. openai/gpt-oss-20b:free
    4. meta-llama/llama-3.3-70b-instruct:free
    5. google/gemma-3-12b-it:free

  If one model returns HTTP 404 (unavailable) or HTTP 429 (rate-limited),
  the system automatically tries the next model. This ensures high uptime
  without any user intervention.

  API Configuration:
    - Endpoint: https://openrouter.ai/api/v1/chat/completions
    - Auth: Bearer token from OPENROUTER_API_KEY environment variable
    - Max tokens: 600 (to keep answers concise)
    - Temperature: 0.4 (balanced between creativity and accuracy)
    - Timeout: 30 seconds

4. TECHNICAL WORKFLOW — 5 STAGES (PER-QUERY LIFECYCLE)
================================================================================

STAGE 1 — USER INPUT
─────────────────────
  File: app.py → /api/ai/chat route (line 1663)
  The user types a natural language question into the chat interface
  (either the retailer assistant page or the Sage bubble on customer pages).
  The question is sent as a POST request with JSON body: {"message": "..."}

  Example: "Which products are low stock and what should I restock first?"


STAGE 2 — METADATA INJECTION (Database Context Building)
──────────────────────────────────────────────────────────
  File: prompts.py → get_retailer_db_context() (line 44) or
                     get_customer_db_context() (line 125)

  Before the question reaches the LLM, our code executes a PACK of prepared
  SQL queries against the LIVE MySQL database to build a comprehensive data
  context. This is the metadata injection step.

  For RETAILER mode (5 query pack):
    Query 1: All products with name, price, stock, status, and units sold
    Query 2: Total revenue and order count (excluding cancelled orders)
    Query 3: Orders grouped by status (pending, processing, shipped, etc.)
    Query 4: Top 5 selling products by units sold
    Query 5: Low stock alerts (products with stock ≤ 10)

  For CUSTOMER mode (7 query pack):
    Query 1: Store overview stats (total products, price range, stock counts)
    Query 2: All active products with ratings, reviews, units sold, discounts
    Query 3: Top 8 most popular products (by sales volume)
    Query 4: Top 8 highest rated products (by average rating)
    Query 5: New arrivals (10 most recently added products)
    Query 6: On sale / discounted products (sorted by discount percentage)
    Query 7: Category breakdown with product counts and price ranges

  The query results are formatted into a structured text block like:
    === YOUR PRODUCTS ===
    - Noise Cancelling Headphones: Rs 18500, Stock=24, Status=Active, Sold=3
    - 4K Action Camera: Rs 27999, Stock=12, Status=Active, Sold=1
    ...
    === FINANCIALS ===
    - Total Revenue: Rs 189000
    - Total Orders (non-cancelled): 10


STAGE 3 — PROMPT CONSTRUCTION & LLM CALL (Query Generation)
─────────────────────────────────────────────────────────────
  File: prompts.py → build_messages() (line 358) and call_ai() (line 427)

  The system prompt (RETAILER_SYSTEM or CUSTOMER_SYSTEM), the live data
  context, and the user's question are combined into a single message:

    ┌────────────────────────────────────────────────────────────────┐
    │  [SYSTEM PROMPT]                                              │
    │  You are Sage, the strategic retail copilot inside Shopy...   │
    │  Rules: Use ONLY the PROVIDED STORE DATA...                   │
    │                                                               │
    │  [LIVE STORE DATA]                                            │
    │  === YOUR PRODUCTS ===                                        │
    │  - Noise Cancelling Headphones: Rs 18500, Stock=24...         │
    │  === FINANCIALS ===                                           │
    │  - Total Revenue: Rs 189000...                                │
    │                                                               │
    │  User question: Which products are low stock?                 │
    │                                                               │
    │  Answer (be concise, use bullet points for lists):            │
    └────────────────────────────────────────────────────────────────┘

  This combined prompt is sent to the OpenRouter API. The LLM reads the
  schema/data context and generates an informed, accurate answer.

  Schema Linking is handled naturally:
    - If user says "clients" → LLM maps to Users table from the context
    - If user says "purchases" → LLM maps to Orders from the context
    - If user says "items" → LLM maps to Products from the context
    The system prompts explicitly instruct the LLM to use only provided data.


STAGE 4 — SAFE EXECUTION (Security Validation)
───────────────────────────────────────────────
  File: prompts.py → call_ai() (line 427)
  File: security.py → validate_user_input(), validate_ai_output() (Phase 3)

  In our architecture, the LLM does NOT generate SQL queries that get
  executed against the database. Instead:
    1. Pre-built read-only SQL queries run BEFORE the LLM call (Stage 2)
    2. The LLM only receives TEXT output from those queries
    3. The LLM generates a TEXT response (not SQL)
    4. Security filters validate both input and output (Phase 3)

  This design eliminates the SQL injection risk at the AI layer entirely.

  Additional safety:
    - API calls have a 30-second timeout
    - HTTP 402 (no credits) returns a clear error message
    - Model failover handles temporary outages
    - <think>...</think> blocks from reasoning models are stripped


STAGE 5 — SYNTHESIS & RESPONSE (Answer Display)
────────────────────────────────────────────────
  File: app.py → ai_chat() route (line 1663-1710)

  The LLM's response is captured and returned to the frontend as JSON:
    {
      "reply": "Your low stock items are...",
      "query_ran": "User Question: ...\nPrepared Query Pack:\n1. SELECT ...",
      "db_output": "=== YOUR PRODUCTS ===\n- Headphones: Rs 18500..."
    }

  The frontend renders THREE sections for transparency:
    1. "Query Ran"      — Shows which SQL queries were executed
    2. "Database Output" — Shows the raw data retrieved from DB
    3. "Final Answer"    — The LLM's human-readable response

  This Debug/Query Inspector panel demonstrates full transparency and
  proves that answers are dynamically generated from live data.

6. CHAT HISTORY PERSISTENCE
================================================================================
  File: app.py → _insert_ai_chat_row() (line 1639)
                  ai_history() route (line 1713)

  Every conversation turn (user message + bot response) is persisted in
  the ai_chat_history table. This enables:
    - Chat history loading when users reopen the assistant
    - Structured bot messages stored as JSON (query_ran + db_output + answer)
    - Legacy schema compatibility (graceful fallback if 'role' column missing)
    - Last 40 messages returned chronologically on page load

================================================================================
9. DYNAMIC BEHAVIOR PROOF
================================================================================
The system is fully dynamic — NOT hardcoded:
  1. If a retailer adds a new product → the next query to Sage will include it
  2. If stock changes → Sage's low-stock alerts update immediately
  3. If new orders arrive → revenue and order count reflect in real-time
  4. If reviews are posted → product ratings update in Sage's context

This is because every AI query re-executes the SQL query pack against the
live database BEFORE sending context to the LLM. No cached or static data.
