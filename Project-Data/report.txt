DOMAIN JUSTIFICATION
────────────────────
We selected the E-Commerce domain because it naturally and organically
produces a rich set of inter-related entities. A real online marketplace
requires users who are either shoppers or sellers, products belonging to
categories, orders that contain many products, payments and shipments
per order, user reviews and wishlists, and promotional discount codes —
all producing genuine many-to-many relationships that must be resolved
through junction tables. E-Commerce data changes constantly (stock
updates, new orders, fresh reviews) making the live, dynamic nature of
our AI assistant clearly visible during every demonstration.

NORMALIZATION STATEMENT — 3NF
──────────────────────────────
  1NF: Every column holds exactly one atomic value. Addresses, phone
       numbers, and product images are stored in their own dedicated
       rows — no comma-separated multi-values anywhere.

  2NF: Every non-key column depends on the FULL primary key. All
       tables use single-column AUTO_INCREMENT surrogate PKs, so 2NF
       is automatically satisfied across the schema.

  3NF: No non-key column depends on another non-key column.
       - Shipping city/province live in the addresses table, not in
         orders (which only stores a snapshot shipping_address string).
       - Category details live in categories, not duplicated in
         products.
       - Payment details live in payments, not repeated in orders
         (orders only stores the method and a reference code).
       - Courier tracking lives in shipments, not in orders.

FOREIGN KEY CONSTRAINTS
───────────────────────
  Every inter-table reference uses an explicit FOREIGN KEY declaration
  (not just matching column names). Cascade rules:
    ON DELETE CASCADE  — child rows removed when parent is deleted
    ON DELETE SET NULL — child FK set to NULL (where data must persist
                         for historical record, e.g. order_items after
                         a product is soft-deleted)

PRIMARY KEY DECLARATIONS
─────────────────────────
  Every table declares a single-column INT AUTO_INCREMENT PRIMARY KEY.
  Junction tables additionally enforce UNIQUE KEY constraints on their
  composite pairs (e.g., UNIQUE KEY uq_cart_user_product (user_id,
  product_id)) to prevent duplicate rows while retaining a surrogate PK.
